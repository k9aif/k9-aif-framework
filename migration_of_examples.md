# Migration: `examples/` → `k9-aif-examples`

Status: **planning only, not scheduled** — target window is next month
(2026-10). Nothing in this document has been executed. See
`project_k9_aif_examples_repo_split.md` in Claude's memory for the original
decision and why (k9chat outgrew "example" — its own container deployment,
its own feature set — and keeping it inside the framework repo blurs the
line between "the framework" and "an app built on the framework").

The target repo (`k9-aif-examples`, `github.com/k9aif/examples`) already
exists and is cloned at `~/ai/k9-aif-examples`, currently holding unrelated
prior work (`Work-In-Progress/`) that must not be touched by this move.

## Scope decision still open

Does this move **all** of `examples/` (13 apps: `K9X_Enterprise_Insurance_
OperationsCenter`, `acme_health_insurance`, `acme_support_center`,
`diagrams`, `k9chat`, `k9routing`, `myapp`, `n8n_helloworld`,
`prompt_evaluation`, `rfp_analyzer`, `weatherAssistLang`, `weather_assist`,
`zero_trust_execution_demo`), or just k9chat, with the rest staying as
lightweight in-repo framework demos? This changes the size of the impact
analysis below significantly — everything here was scoped against a
full-folder move (the larger, worse case) so it's a safe upper bound either
way.

## Impact analysis

Full-workspace grep across every repo under `~/ai/` for references to
`k9-aif-framework/examples` or `examples/<app-name>` (run 2026-09-21).
Grouped by what actually breaks vs. what just goes stale.

### A. Real functional/deployment dependencies — would break

| File | What breaks |
|---|---|
| `scripts/k9x_containers.sh` | App dispatcher hardcodes `k9-aif-framework/examples/K9X_Enterprise_Insurance_OperationsCenter/ubuntu` for the `eoc` entry |
| `scripts/k9chat_container/ubuntu/Containerfile` + `build-run.sh` | `COPY ${K9AIF_DIR}/examples/k9chat` — build fails outright without a path update |
| `k9-aif-graph/app_backend.py` | `/api/examples/k9_chat`, `/api/examples/acme_support_center`, `/api/examples/das` endpoints call `graph_service.run_view("examples/k9_chat")` etc. — a Neo4j view keyed by that literal path string |
| `.claude/settings.local.json` (this repo's own pre-approved Bash permissions) | Hardcodes `examples/K9X_Enterprise_Insurance_OperationsCenter/tests/...` — permission re-prompts resurface after the move, not a functional break but a friction regression |

### B. Scaffold-generator template strings — stale pointers baked into every future generated project

Three **separate, duplicated** copies of `scaffold_service.py` (`studiox_v2`,
`studiox_ibm`, `k9x-ecosystem/k9x_studio`) embed comments like
`"# or Redis (see the EOC example in k9-aif-framework/examples/ for a..."`
as literal string content written into every newly generated project's own
source comments. Not a functional break (it's a comment), but every future
scaffold from any of these three would point new users at a dead path until
all three copies are updated. Worth noting as its own follow-up: three
duplicated copies of the same generator is a pre-existing maintenance smell
independent of this migration.

### C. Documentation/CLI text — goes stale, nothing crashes

- `k9_aif_abb/cli.py` — the framework's own `k9aif --help examples` text
  hardcodes `examples/` paths and descriptions (real user-facing CLI help,
  should be updated but isn't a break)
- This repo's own docs: `README.md`, `CHANGELOG.md`, `SKILLS.md`,
  `old-CLAUDE.md`, `setup.md`, `docs/getting-started.md`,
  `docs/developers/Developer-guide.md`
- Other repos' context docs that point developers at the framework's
  examples for reference: `dow-k9-aif/CLAUDE.md`, `studiox_v2/context/
  CLAUDE.md`, `studiox_ibm/context/SKILLS.md`, `k9x-ecosystem/k9x_studio/
  context/SKILLS.md`
- `k9-aif-patterns` repo's pattern docs
- `scripts/schemas/02_create_minio_buckets.py` — one comment citing an EOC
  file path for context
- Historical content, probably not worth retroactively editing: 5 blog
  posts under `k9-aif-blogs/_posts/`, 4 files in the `k9x-publication`
  book manuscript

### D. Hand-maintained public page — needs a real content update, not a broken link

`docs/examples/index.html` in this repo is the actual source for
`pydocs.k9x.ai/examples/` (confirmed via git log — hand-edited, not
generated by `generate_pdoc.sh`). `doit/index.html` and `doit/
developer_guide.html` link to that **hosted URL**, not a local path, so
they don't break mechanically — but the hosted page's own content (example
list, descriptions) needs updating to match wherever things actually moved.

## Suggested phased approach (not started)

1. Lock the scope decision (all of `examples/` vs. k9chat only)
2. Fix category A (real breaks) in the same PR as the actual move
3. Fix category B (scaffold templates) in a follow-up PR — affects future
   generated projects, not urgent same-day
4. Update category C opportunistically, category D as its own content pass
5. Re-run this same grep sweep post-move to confirm nothing was missed
